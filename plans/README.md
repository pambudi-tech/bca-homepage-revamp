## The rule that governs plans 001–015

The repository owner's stated priority at the time, verbatim: *"what i care is
the code is clean and the website is perform well (with the same visual that i
made without any lag)."*

Plans 001–015 are therefore bound by a hard constraint:

> **The site must look pixel-identical after the change. No layout shifts, no
> timing changes, no restyling.** If a change cannot be made without altering
> what the user sees, it does not belong in these plans — stop and report
> instead.

## The rule that governs plans 016–021 — READ THIS

Batch 3 is a **design-system batch**, and the owner explicitly relaxed the rule
above **for these six plans only**:

> For plans 016–021, visual consistency beats preserving current pixels exactly.
> Where a value has drifted from its own pattern, normalising it is correct even
> though something moves on screen.

This is **not retroactive.** Plans 001–015 remain bound by the pixel-identical
rule. Do not cite batch 3's latitude when executing or re-executing an earlier
plan.

Even inside batch 3, the latitude is bounded:

- Every deliberate visual change is **named in the plan that makes it**. There
  are only five in the whole batch: `MyBcaSection.tsx:42` gains a hover state
  (016), `FaqSection.tsx:331` and `SoliprioSection.tsx:90` normalise onto the
  type scale (017), `PromoSection.tsx:137` and `SearchRecommendation.tsx:269`
  normalise onto `--shadow-card` (018), and `NewsSection.tsx:335` gains a hover
  state (020).
- Every one requires **before/after screenshots in the executor's report**.
- Anything *not* on that list must still come out pixel-identical. An
  unexplained visual difference is a bug, not licence.

### Constraints that still bind every plan, all batches

Converting `<img>` to `next/image` is **explicitly ruled out**. It is the single
largest available loading-speed win, and the owner declined it because the hero
and product cards use layered subject/background compositions with hand-tuned
CSS. The 84 `@next/next/no-img-element` lint warnings are expected and
deliberate — do not "fix" them.

**`archive/` is never touched by any plan.** It holds reference snapshots
(`PercentGlass.tsx`, `SoliprioSection.tsx`, `ProductSection.tsx`, and
`lokasi-bca/`), is excluded from `tsconfig.json` and ESLint, and is imported by
nothing.

## Dependency notes

Dependencies are derived from **file overlap**, which is stricter than logical
dependency — two plans editing the same file must run sequentially or their
diffs conflict.

### Batch 3

- **016 → 017 → 018 → 019 are strictly sequential.** All four append to the
  same `@theme` block in `src/app/globals.css`, each positioned after the
  previous one's section. Running them out of order or in parallel guarantees
  conflicts.
- **020 requires 016, 017 and 019.** Its `@utility` blocks reference
  `--color-primary*` (016) and it converts call sites that 017 also touches.
  Note the failure mode: a missing color token does **not** fail the build — the
  buttons simply render transparent. 020 carries a `grep` precondition for this.
- **021 requires all of 016–020.** It documents the token system; running it
  early documents something that does not exist.
- **018 and 017 share call sites.** Several elements carry both a type recipe
  and a `[text-shadow:…]`. Each plan explicitly forbids touching the other's
  fragment; that boundary is what keeps the two diffs disjoint.

### Batch 2 (historical)

- 010 required 009; 012 required 008 and 011; 014 required 013. All landed.

## What each batch-3 plan does, in plain terms

- **016** — Every primary button on the site pastes its own hover and active
  colors as raw hex (`#0068c0`, `#00457f`). Neither exists in the theme; one
  button has already lost its hover state entirely. This gives them names.
- **017** — The section heading is copy-pasted across six files, and 32
  hand-written letter-spacing values encode just two rules (−0.02em for
  headings, +0.15em for eyebrows) spelled five different ways in absolute
  pixels. This makes the rule the source of truth.
- **018** — One text shadow is written out 17 times. One card shadow is written
  three different ways in three files, and one copy has silently lost a layer.
- **019** — The house easing curve appears 14 times as a magic number, and 18
  more call sites spell out values Tailwind already names (`ease-in-out`,
  `ease-in`). Every substitution is value-identical.
- **020** — 67 buttons, no shared button. The main CTA's twelve-class string
  lives in five files, with a code comment in `HaloBcaChat.tsx` *instructing*
  future developers to keep the copies in sync by hand.
- **021** — `README.md` is still the create-next-app template telling new
  developers the font is Geist and pages live at `app/page.tsx`. Also writes
  `docs/design-tokens.md`, without which the work above is undiscoverable.

## Findings considered and rejected

Recorded so nobody re-audits them.

### From the 2026-08-03 pass

- **Restructuring `src/components/home/`** — 49 files in one flat directory,
  mixing page sections, nav chrome, shared primitives, seasonal decor and
  fallback data; `src/lib/` similarly mixes 7 fetchers, 3 hooks and 2 utils.
  Real, and a genuine readability cost. **Not planned in this batch** by the
  owner's choice: it rewrites imports across ~50 files for zero behaviour
  change, and doing it *after* the token work means one churn instead of two.
  Worth revisiting as its own batch.
- **Splitting `ProductSection.tsx`** — 1,659 lines and 8 components in one
  file, ~370 of them the unreachable `curved` variant. Same reasoning as above:
  real, deferred by choice, best done as its own focused change rather than
  tangled with the token migration.
- **Deleting the frozen `curved` / `glass` variants** — the owner's comment at
  `ProductSection.tsx:1209-1210` says they are kept intentionally. Deleting
  them is a product decision, not a cleanup.
- **Seven Indonesian comments in otherwise-English source**
  (`ProductSection.tsx:799,802`, `news-data.ts:50`, `lib/news.ts:67,119`) and
  an Indonesian `supabase/README.md` against an English `README.md`. Noted, not
  planned. New docs are English (owner's choice, 2026-08-03); existing
  Indonesian content stays.
- **`LayoutSwitcher` is dead code** — investigated and **false**. It is still
  rendered by `HeroWidget.tsx:301`, `MobileHeroWidget.tsx:472` and
  `PromoSection.tsx:290`. It is prototype scaffolding shipping to production,
  which is already recorded under "Known follow-ups" — not a new finding.
- **Tokenizing the remaining ~101 hex and ~139 `rgba()` literals** — most are
  legitimate one-offs: seasonal decor artwork (`cny-art.ts`,
  `christmas-art.ts`, `decor-kit.ts`), the confetti palette, and individual
  gradient stops. Only the interaction-state pair is a system value. Plan 016
  is deliberately narrow.
- **Tokenizing the nine single-use shadows and the `drop-shadow()` stacks in
  `globals.css`** — a token with one call site is a rename. The `drop-shadow()`
  triples additionally carry a load-bearing comment ("`filter` only interpolates
  between lists of matching length") and must not be restructured.
- **Tokenizing durations** — already consistent (150/200/300/500/700) and all
  stock Tailwind utilities. Churn for no gain. Plan 019 explicitly excludes them.
- **Folding `CookieBanner`'s buttons and the hero CTA into `btn-primary`** —
  they share a border radius and nothing else: different transition properties,
  an `active:scale-95` press, breakpoint-dependent sizing, and in the hero's
  case an inverted fill. Converting them would need more overrides than they
  have classes today. Plan 020 excludes all three by name.
- **Adding a React `<Button>` component instead of a CSS utility** — the eight
  call sites are a mix of `<button>` and `<a>` with different `target`/`rel`
  props; a component needs polymorphic `as`/`asChild` plumbing for the same
  result. Reconsider only if a props-driven API is actually wanted.

## Known follow-ups, deliberately not planned

Decisions someone should make before this site goes live:

- **`/tentang-bca` is an empty shell** that the navbar links to with a
  view-transition treatment. Plan 015 marks it `noindex` and keeps it out of
  the sitemap, but it still needs either real content or a hidden link.
- The auth cookie stores the shared preview password verbatim
  (`login/page.tsx:15`) rather than a derived token. Changing it logs out every
  existing preview session.
- The HaloBCA chat's reCAPTCHA falls back to Google's public always-pass test
  key when `NEXT_PUBLIC_RECAPTCHA_SITE_KEY` is unset, and no token is verified
  server-side because no chat backend exists yet.
- `LayoutSwitcher` / `useLayoutVariant` is self-described "Prototype-only" demo
  scaffolding that ships to production unless someone strips it. Still rendered
  in three places (`HeroWidget.tsx:301`, `MobileHeroWidget.tsx:472`,
  `PromoSection.tsx:290`).
- The preview gate silently disappears when `PREVIEW_PASSWORD` is unset
  (`src/proxy.ts:26`) — safe by accident rather than by design.
- Nothing on the page is measured: searches, promo clicks and category switches
  emit no analytics, so the search corpus is being tuned blind.
- The search corpus is Indonesian-only, so English and Chinese queries often
  return nothing even after plan 006.
- **New, raised by plan 020**: `CookieBanner.tsx:181` hovers to `blue-400`
  (`#1179d1`) where every other primary button hovers to `primary-hover`
  (`#0068c0`). One of the two is wrong; it needs a design decision, not an
  executor's guess.
- **New, raised by the 2026-08-03 pass**: the flat 49-file
  `src/components/home/` directory and the 1,659-line `ProductSection.tsx`.
  Both are real readability costs, both deferred deliberately (see "Findings
  considered and rejected"), both worth their own batch once the tokens land.
